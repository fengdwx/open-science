**Open Science 会话存储优化说明：10 轮对话测试**

2026-10-14｜本地实现与测试结果

本次优化在持续保存和对话展示读取上取得了收益：三个场景合计，新增追问的保存处理耗时下降 **32.99%**，会话文件累计写入量下降 **97.27%**，打开对话时的后端读取耗时下降 **85.10%**。同时，继续追问、分叉或导出时需要的完整历史加载仍有退步，耗时为原版的 **2.22 倍**。目前不能据此宣称整个对话流程全面提速。

这项改动目前应定位为**减少重复写入和后台保存成本**。拆到单个样本，打开对话的后端读取只减少约 **12～29 ms**，尚未验证用户能否感受到明显差异；不能把百分比直接表述为界面明显更快。

表中性能数据来自本轮正确性修复之前的 10 轮冻结版本；本轮提交版本的正确性检查另行记录，尚未重跑这套性能基准。

历史基准使用单帧、单分支样本进行线性追问。当前实现中，包含修订分支或复杂会话层级的会话仍完整读取，以保留原有导航功能；表中的分页读取收益不适用于这些会话。

在排查 SkillOps 性能、调研 Codex 和 DSH 的会话存储思路时，发现 Open Science 原来的保存方式会反复处理并写入完整会话，即使只是新增少量正文或工具结果，也会重复处理已经保存的历史。本次针对这部分重复工作做了调整：**新会话采用 JSONL 追加业务记录，并支持分页读取；旧 JSON 保留原来的读写路径，不自动迁移；保留原约 2 秒合并保存的策略。** 旧记录不会自动获得新格式的分页收益。

测试使用官网三个完整 `.science` 记录——投资比较、分子手性和百年降雨——作为基础，按原记录的回复长度、工具调用和结果规模模拟后续追问，将每个会话补到 **10 次用户提问**。三个场景、三种存储路径分别独立测试 6 次。

**业务场景对比**

下表数值为三个场景各自中位数的合计，不是一个会话的耗时。最后一列统一比较“新 JSONL”与“修改前 JSON”。

| 业务场景与指标                             | 修改前 JSON | 修改后旧 JSON（兼容路径） | 修改后新 JSONL | 新 JSONL 的变化              |
| ------------------------------------------ | ----------: | ------------------------: | -------------: | ---------------------------- |
| 持续追问：自动保存累计处理耗时             |    13.56 秒 |                  12.30 秒 |        9.09 秒 | 减少 32.99%                  |
| 持续追问：会话文件累计写入量               |   320.41 MB |                 320.41 MB |        8.73 MB | 减少 97.27%                  |
| 打开对话、查看最近记录：后端读取耗时       |    73.64 ms |                  71.51 ms |       10.97 ms | 减少 85.10%                  |
| 查看当前分支的全部历史：后端读取耗时       |    83.37 ms |                  72.91 ms |       19.42 ms | 减少 76.71%                  |
| 继续追问、分叉或导出：完整历史加载步骤耗时 |    71.32 ms |                  73.12 ms |      158.09 ms | 增加 121.66%，为原版 2.22 倍 |

**收益主要来自减少重复处理和写入历史，以及按需读取展示数据。** 本次新增追问累计少花约 **4.47 秒**处理保存，少写约 **311.67 MB** 会话文件。这些是存储处理成本的降低，不代表模型生成回复变快，也不等于磁盘占用减少同样的容量。

**完整历史加载变慢会影响真实业务，不能只视为偶发的崩溃恢复成本。** 普通浏览可通过分页读取最近记录；当前继续提问的运行启动路径仍会读取完整会话，包括消息、工具记录、分支和运行状态。JSONL 完整加载需要读取并应用追加记录；本次没有逐步骤拆分耗时，不能把全部差额归因于某一个步骤。分子手性、投资比较、百年降雨三个样本的一次完整加载分别多花约 **13.77、25.41、47.59 ms**。这只是完整加载这一步的差额，尚未测量它们对发送问题到开始回复的总延迟有多大影响。

**测试范围与验证**

- 保存累计只统计新增的 7、7、6 轮模拟追问，每次重复共 326 次保存；原始历史及前置控制轮不计入。保存耗时包含状态处理、SQLite 更新与会话文件同步，不包含模型生成、工具执行、约 2 秒调度等待或界面处理。
- 三种路径使用相同内容，每轮核对消息、工具结果、运行与用量数据、产物引用及分页展示字段；结果一致。旧 JSON 保持原格式，未自动迁移或建立分页索引。
- 读取测的是第 10 轮结束后的后端数据准备，使用新进程但未清空系统文件缓存；不包含界面渲染、模型连接或业务全过程。初始测试副本构造不计时，不代表新建会话或导入文件的完整耗时。
- 打开对话一项中，原版 JSON 完整读取后由基准在内存切页，当前旧 JSON 返回完整会话，新 JSONL 读取最近 80 条业务记录及问题上下文；三条路径不是返回同样大小的数据。
- 累计写入量只统计会话文件，不含 SQLite/WAL、文件系统日志或设备物理写入量；不是最终文件大小。合计值是三个场景中位数相加，不是合并全部样本后再取中位数。
- 本轮性能测试未重新注入崩溃故障，异常恢复结论沿用已有专项验证；这些结果属于本地测试证据，不等于上线验收。

建议保留当前实现与测试证据，后续优先核对继续追问中的完整加载次数、是否存在重复读取，以及实际启动延迟，再决定最小优化范围。现阶段不扩大到自动迁移旧数据或增加压缩机制。
